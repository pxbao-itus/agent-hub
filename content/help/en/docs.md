## When to use a Doc

A Doc is versioned reference material: a specification, decision, investigation,
runbook, or other context that people and agents may need. Use a Plan when the
main purpose is tracking tasks.

## Create and organize a Doc

1. Choose the owner space and visibility.
2. Write a clear title and a short description.
3. Structure the Markdown body around durable concepts and decisions.
4. Add tags for discovery.
5. Link the Doc to a Plan or add it to a Project when it informs active work.

Keep sensitive data and secrets outside the Doc. Visibility is access control,
but it is not a secret-management system.

## Collaboration

A Doc can have an assigner and multiple assignees. Assignment communicates
responsibility; the target user must already be able to view the Doc.

Linked Plans express that work was derived from or informed by the Doc. Project
membership provides project context but does not replace artifact access rules.

Each content update creates a version. Use comparison for review and rollback
when a previous body should become current again. Assignment history and version
history record different events.

Agents can retrieve accessible Docs through MCP resources or tools, depending
on client support.

See [Plans](/help/plans), [Projects](/help/projects), and
[Sharing and assignment](/help/sharing-and-assignment).
